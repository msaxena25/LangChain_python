# What is LLM evaluation?

LLM evaluation is the `process of measuring how well an LLM performs` and whether its responses meet the expected quality, accuracy, and reliability standards.

**A user asks:** "Find hotels in Jaipur for three guests."

**We need to evaluate whether the application:**

- Understands the user's intent.
- Finds hotels in Jaipur.
- Calculates the required number of rooms correctly.
- Provides accurate prices.
- Does not invent hotel details.

That entire process comes under LLM application evaluation.

# Two broad categories of LLM evaluation

## A. Model-level evaluation

This evaluates the capabilities and limitations of an LLM independently of a particular business application.

**For example, evaluating a model's:**

- Reasoning capabilities.
- Mathematical problem-solving.
- Coding capabilities.
- Language understanding.
- Instruction following.
- General knowledge.
- Safety and robustness.

### Who performs it?

Primarily `model developers` and `research teams` working at organizations such as OpenAI, Google DeepMind, Anthropic, and Meta.

They `use benchmarks and specialized evaluation datasets` to measure model capabilities and compare model versions.

## B. Application-level evaluation

This is where your focus as an AI application developer. Here, `we evaluate` whether our complete AI `application performs the intended business task correctly`.

We `evaluate the complete workflow`, not just the final LLM response.

| What we evaluate       | Example                                           |
| ---------------------- | ------------------------------------------------- |
| Intent detection       | Does it understand hotel search vs booking?      |
| Response accuracy      | Does it return correct hotel details?             |
| Tool selection         | Does it call the correct tool?                    |
| Tool arguments         | Does it pass the correct city and dates?         |
| RAG quality            | Does it retrieve relevant information?            |
| Calculation accuracy   | Does it calculate rooms and prices correctly?    |
| Context handling       | Does it remember the selected hotel?              |
| Hallucination          | Does it invent hotels or prices?                  |
| Safety                 | Does it avoid booking without confirmation?       |

# Major evaluation approaches

There are three major evaluation approaches commonly used in LLM application evaluation:

1. Programmatic / Deterministic Evaluation
2. Human Evaluation
3. Model-Graded Evaluation (LLM-as-a-Judge)

## 1. Programmatic / Deterministic Evaluation

In this approach, we `use normal Python code, exact match, calculations, predefined rules.` to evaluate the LLM application's output. We don't need another LLM to judge the result.

Use this technique where we have a clearly defined expected result.

Example: "Book a Deluxe room in Jaipur for 3 guests."

We can create our custom function, rules to find out hotels.

**Where can we use this method?**

- Checking extracted dates.
- Checking hotel names and cities.
- Validating room counts.
- Checking price calculations.
- Checking whether the correct tool was called.
- Checking whether booking confirmation was obtained.

## 2. Human Evaluation

Here, a human evaluator `manually reviews the LLM's responses` and determines whether they are good enough. Use where situations requiring human judgment.

User query: "Suggest a good family hotel in Jaipur."

**LLM response:**

"Hotel Oberoi is a suitable option for a family stay. It offers premium accommodation and family-friendly facilities."

**A human evaluator checks:**

- Is the answer relevant?
- Does it actually address the user's requirement?
- Is the explanation clear?
- Is the tone appropriate?
- Is the information factually correct?

The evaluator can `assign scores` using a predefined rating scale.

| Score | Meaning    |
| ----- | ---------- |
| 1     | Very poor  |
| 2     | Poor       |
| 3     | Acceptable |
| 4     | Good       |
| 5     | Excellent  |

Where can we use this method?

- Evaluating response quality.
- Checking naturalness and readability.
- Evaluating whether recommendations are useful.
- Identifying subtle hallucinations.
- Evaluating complex answers where there is no single exact expected answer.

## 3. Model-Graded Evaluation (LLM-as-a-Judge)

In this approach, we `use another LLM` to evaluate the response generated by our application.

Use where Evaluating open-ended responses & exact matching is not practical.

User query: "Suggest a hotel in Jaipur suitable for a family."

**Application response:**

"Hotel Oberoi is a good option for a family stay."

**We send the following to another LLM:**

```
You are an evaluation assistant. Evaluate the application response based on:

1. Relevance
2. Accuracy
3. Completeness

User Query:
Suggest a hotel in Jaipur suitable for a family.

Application Response:
Hotel Oberoi is a good option for a family stay.

Provide a score from 1 to 5
for each evaluation criterion.
Explain your reasoning.
```

**The judge LLM might return:**

```py
{
    "relevance": 5,
    "accuracy": 3,
    "completeness": 2,
    "reason": "The response is relevant but provides insufficient supporting details."
}
```

# LLM evaluation lifecycle

1.`Define success criteria`: Decide what a successful application response looks like.

   Example: 95% correct hotel search results.

2.`Build an evaluation dataset`: Prepare test queries with expected outputs or expected behaviour.

   Example: 100 hotel-search and booking scenarios.

3.` Define evaluation methods`: Decide how you will measure performance.

   Example: Exact match, correctness checks, LLM-as-a-judge, human evaluation.

4.`Run the application`: Execute your test dataset against the application and capture its responses, tool calls and intermediate results.

5.`Evaluate the results`: Compare actual outputs with expected results using your evaluation methods.

6.`Analyse the results`: Identify failures and their root causes.

   Example: Incorrect date extraction or wrong tool selection.

7.`Improve the application`: Modify prompts, models, retrieval logic, tools, or application code.

8.`Run the evaluation again`: Check whether the changes improved performance without breaking previously working scenarios.

Continuous evaluation and improvement

# Retrieval Evaluation with Recall@K and Precision@K metrics

To quantify whether a retriever is working properly, we `evaluate its retrieval quality`: whether it retrieves the right documents for a given query, and whether it `ranks` the most relevant documents near the top.

## 1. First, create a retrieval evaluation dataset

We need test queries and their expected relevant documents.

For example:

| Query                                | Expected relevant documents |
| ------------------------------------ | --------------------------- |
| Hotels in Jaipur with swimming pools | D1, D3, D5                  |
| Hotels in Delhi under ₹5,000         | D2, D4                      |
| Hotels with family rooms             | D6, D7, D8                  |

These expected documents are our **ground truth**. They can be identified manually by reviewing the documents.

### A. Precision\@K Metrics

It measures: **Out of the top K documents retrieved, how many are actually relevant?**

Suppose:

- Expected relevant documents: D1, D2, D3
- Retrieved top 5: D1, D5, D2, D7, D8
- Relevant retrieved documents: D1, D2

```
Precision\@5 = 2 / 5 = 0.40 = 40% precision
```

**This means 2 out of the 5 retrieved documents are relevant.**

### B. Recall\@K

It measures: **Out of all relevant documents available, how many did the retriever successfully retrieve?**

Using the same example:

- Total relevant documents: 3
- Relevant retrieved documents: 2

```
 Recall\@5 =  2 / 3 = 0.667 = 66.7% recall
```

This means the **retriever found approximately 67% of all relevant documents**.

**Difference:**

- Precision: How many retrieved documents are relevant?
- Recall: How many relevant documents did we successfully retrieve?

# Humans' Involvement in AI Evaluation

Human involvement in AI evaluation can be categorized into two areas:

## 1. Human Evaluation Techniques

Humans directly grade AI-generated responses to measure their quality, correctness, and usefulness.

1\. **Direct Grading / Rating**: A human evaluator `reviews an individual response and assigns a score` (e.g., 1–5) based on defined criteria such as accuracy, relevance, and completeness.

2\. **Pairwise Comparison**: Give the same query to Gemini and Qwen. Ask a human evaluator which response is more accurate and relevant based on predefined criteria.

3\. **Rubric-Based Evaluation**: Evaluators use a `predefined evaluation matrix (rubric) containing criteria, scoring levels, and descriptions` to grade AI responses consistently.

- One, Two Or Multiple human evaluators can independently grade the same responses.
- Their scores are compared to identify disagreements.
- The rubric is refined by clarifying criteria and scoring guidelines.
- `Inter-rater reliability` measures the consistency of different evaluators (explained below).

4\. **Error Identification / Annotation**: Evaluators identify and categorize errors in AI responses, such as incorrect information, missing details, wrong tool selection, or irrelevant answers.

## 2. Human Involvement in Testing and Validating

Humans participate in preparing, validating, and testing AI applications to improve their reliability and performance.

1\. **Gold Dataset Creation**: Humans or domain experts `create and validate a dataset containing trusted reference answers`. These datasets are used to measure AI application performance.

2\. **Red Teaming**: Humans deliberately `test AI applications with unexpected inputs` to identify vulnerabilities, unsafe responses, prompt injection, and security issues.

3\. **A/B Testing**: Release Two application's Version `A using Gemini` to one group of users and `Version B using Qwen` to another group. Human evaluators test different versions of an AI application to compare their performance, usability, success rate, user satisfaction, response time, etc.

4\. **Human-in-the-Loop (HITL)**: Humans participate in the AI workflow by `reviewing, correcting, approving`, or rejecting AI-generated results before critical actions are performed.

# Inter-Rater Reliability (IRR)

Suppose you have **created a rubric** to evaluate whether your AI gives a good hotel recommendation.

You ask three human evaluators to check the same 5 AI responses and assign a score from 1 to 5.

| AI response | Evaluator 1 | Evaluator 2 | Evaluator 3 |
| ----------- | ----------- | ----------- | ----------- |
| Response 1  | 5           | 5           | 4           |
| Response 2  | 4           | 4           | 5           |
| Response 3  | 2           | 2           | 2           |
| Response 4  | 5           | 2           | 1           |

**Now observe:**

- For Response 1, all evaluators gave almost the same score.
- For Response 2, their scores are also very close.
- For Response 3, all evaluators completely agree.
- For Response 4, their scores are very different.

What does this tell us?

Evaluators generally agree, but Response 4 creates confusion.

**We can discuss this disagreement, improve the rubric, and ask evaluators to grade the responses again.**

That's the` basic idea of Inter-Rater Reliability`: checking whether different people give similar scores when evaluating the same thing.

### What are Cohen's Kappa, Fleiss' Kappa, and ICC?

These are simply `statistical methods` used to measure that agreement.

| Method        | When do we use it?                             | Simple example              |
| ------------- | ---------------------------------------------- | --------------------------- |
| Cohen's Kappa | Two evaluators                                 | Evaluator A vs. Evaluator B |
| Fleiss' Kappa | Three or more evaluators                       | Evaluator A, B, and C       |
| ICC           | Multiple evaluators assigning numerical scores | Scores from 1 to 5          |

# Reference-Based Evaluation VS Reference-Free Evaluation

### 1. Reference-Based Evaluation

In this approach, we compare the AI-generated response with a **predefined correct answer** (reference answer or ground truth) to evaluate its accuracy.

Example:

- User query: What is the capital of India?
- Reference answer: New Delhi.
- AI response: New Delhi.

### 2. Reference-Free Evaluation

In this approach, we evaluate the AI response without having a predefined correct answer.

Instead, we use evaluation `criteria such as relevance, correctness, completeness, and clarity`. Evaluation can be performed by humans by theri own judgement, second by an LLM judge.

Example:

- User query: Recommend three family-friendly hotels in Delhi.
- AI response: Provides three hotels with prices, ratings, and family-friendly facilities.

# Online Evaluation (Online Evals)

Online evaluation means `evaluating an AI application` while it is being used by real users `in a production environment`.

Example: Hotel Booking AI

Suppose your AI application is live.

You monitor:

- Success rate: How many users successfully complete hotel searches or bookings?
- Response quality: Are AI responses relevant and accurate?
- Tool accuracy: Is the AI selecting the correct tools?
- Latency: How much time does the AI take to respond?
- User feedback: Are users satisfied with the responses?

### How do we perform online evaluation?

1. Collect real user queries and AI responses.
2. Capture execution traces, tool calls, and results.
3. Evaluate them using automated checks, LLM judges, or human feedback.
4. Analyze failures and improve the application.

# Post-Deployment Risks in AI Applications

## 1. Unanticipated Inputs

These are `unexpected, incomplete, unsupported, or out-of-scope inputs` that the AI application was not specifically designed or tested to handle.

Examples – Hotel Booking AI:

1. Incomplete information: User says, "I want a hotel." The AI doesn't know the city, dates, or number of guests.
2. Different language: User asks, "Mujhe Delhi mein hotel book karna hai." But the application was primarily tested with English inputs.
3. Out-of-scope request: User asks, "Can you suggest a flight to Mumbai?" But the application only supports hotel booking.

**How to handle it:** Input validation, clarification questions, language handling, intent detection, and appropriate fallback responses.

## 2. Emergent Systematic Failure

This is when a failure pattern emerges in a deployed AI application and `repeatedly affects` multiple users or requests.

Example – Hotel Booking AI:

Suppose your application is deployed and thousands of users start using it.

- Due to a prompt or tool-integration issue, the AI consistently extracts incorrect checkout dates.
- The same incorrect date calculation happens across many booking requests.
- As a result, users receive incorrect booking prices.

This is a systematic failure because the same underlying issue is repeatedly affecting different users.

Other examples:

- A database connection pool becomes exhausted under concurrent requests.
- A shared prompt change causes the AI to select the wrong tool repeatedly.

## 3. Drift

Drift occurs when input data or real-world patterns change over time (today data will not be fit after 1 year), potentially reducing AI application performance.

- Data Drift: User input patterns change. Example: users increasingly search for hotels in Goa instead of Delhi.

How to handle it: Monitor data and performance trends, periodically evaluate the application, and update datasets, prompts, retrieval sources, or models when needed.

# Diff between Online and Offline Evals

|                | Offline eval (before deployment) | Online eval (after deployment)      |
| -------------- | -------------------------------- | ----------------------------------- |
| Data           | Fixed, pre-collected dataset     | Live production traffic             |
| Answer key     | Known in advance                 | None - must estimate quality        |
| Timing         | Runs before shipping             | Runs continuously, live             |
| Inputs seen    | Only what you anticipated        | The real, messy distribution        |
| Catches        | Known regressions                | Drift, surprises, emergent bugs     |
| Best for       | Gating, version comparison, CI   | Real-world quality, drift detection |
| Cost & speed   | Fast, cheap, repeatable          | Ongoing, needs sampling to afford   |
